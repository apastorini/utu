1.1 TLS: la protección aplicada de un protocolo de aplicación

La clase 47 dio la criptografía. TLS es la aplicación completa, y es lo que justifica toda la clase 47.

      · versión soportada (TLS 1.3)
      · cipher suites  ← ciphers SIMÉTRICOS + hash

                                     · elige cipher suite

                                     · kp del servidor (autenticación)

                                     · MAC sobre todo el transcript
   ◀────────────────────────────────────────────────────

     Los dos Finished exchanged en 1-RTT.

Los cuatro servicios, con el mecanismo exacto que los da:

Servicio Mecanismo en TLS 1.3
Confidencialidad clave de sesión derivada por (EC)DH; cifrado con AES-256-GCM o ChaCha20-Poly1305
Integridad AEAD: el tag de autenticación va en cada registro
Autenticación del servidor certificado X.509 + firma del CertificateVerify
Autenticación del cliente opcional: certificado cliente o SRP / PSK
Forward secrecy (EC)DH efímero: las claves de sesión se borran y no se pueden recuperar

El concepto que hay que entender: el forward secrecy.

   SIN forward secrecy:          CON forward secrecy (PFS):
   ──────────────────────        ──────────────────────────
   El servidor guarda la         El servidor NO guarda la
   clave de sesión.              clave de sesión. Nunca la
   Alguien que roba el           tuvo guardada. Cuando se
   servidor HOY obtiene          termina la conexión, se
   TODO: el tráfico de           borra. Lo único que queda
   AYER descifrado.              es la clave pública (pública).
   ★ "Perfect forward secrecy"   ★ Aunque te entreguen el disco
     significa: aunque te        forense del servidor hoy, no
     entreguen la clave AHORA,    podés descifrar lo de ayer.
     no descifrás lo de AYER.

Y es por eso que el handshake de TLS 1.3 es de 1-RTT: se manda el key_share en el primer mensaje, sin esperar el ServerHello con criptografía clásica (RSA). Antes (TLS 1.2 con RSA) eran 2 RTT. Ese es un avance real y medible.

Y el puerto que se cambia: HTTP en 80, HTTPS en 443. Y ojo: 443 es TCP, no UDP. (El 443/UDP es QUIC, que es otra cosa — clase 9.)

1.2 SSH: el mismo esquema, otro uso

   CLIENTE ─────────── SERVIDOR
      │                    │
      │── kp_srv ─────────▶│   1. el servidor manda su clave de host
      │                    │      (¡EN CLARO! de eso se encarga DNS/DH)
      │◀─ kp_cli (efímera) ─│   2. el cliente manda su clave efímera
      │                    │
      │  secreto compartido │
      │  + HKDF + las claves de cifrado de sesión  ← derived keys
      │                    │
      │◀═══ CANAL CIFRADO ═══▶│   3. de acá en adelante todo va cifrado

Puntos clave de SSH:

  • La clave de host es del servidor, pública, y se publica en el DNS (o en el known_hosts). Se verifica: si cambia, te avisa.
  • Las claves de sesión son efímeras: se renegocian por canal o cada hora. Es lo que da el PFS en SSH.
  • Autenticación del usuario: por clave pública (ideal), o por contraseña (y acá el problema famous: el servidor no recibe la contraseña, sino un valor derivado, así que un sniffer no la obtiene).
  • Canal de control + canales de sesión: el canal de control multiplexa varias sesiones (port forwarding, SOCKS, agent forwarding). Es el mismo concepto de multiplexación de la clase 16, pero en la capa de aplicación.
  • Moderno: por defecto usa Ed25519 para las claves de host y ECDH para el acuerdo (RFC 8709, 2020).

El "ataque del hombre en el medio" en SSH solo funciona si nadie verifica la clave del host. Y la primera conexión pregunta "¿confiás en esta huella?". Si decís que sí sin leer, perdiste. Es exactamente el problema de la raíz de confianza de la clase 47, pero resuelto a nivel de un solo servidor.

1.3 PGP: cifrar correo entre usuarios

PGP (Pretty Good Privacy) es el esquema de seguridad extremo a extremo para correo. La diferencia con TLS es dónde está el protocolo:

   TLS    ──  SEGURIDAD EN EL CAMINO (transport)
            El servidor web la termina: ve todo el tráfico.
            ★ Confiás en el servidor.

   PGP    ──  SEGURIDAD EXTREMO A EXTREMO (aplicación)
            Cifrás el mensaje antes de que salga de tu máquina.
            El servidor de correo TRANSPORTA un texto cifrado.
            ★ El servidor no puede leerlo, aunque lo quiera.

El modelo de claves de PGP (y el detalle fino que se pregunta):

   Cada usuario tiene UNA clave privada y VARIAS claves públicas:

   ┌───────────────────────────────────────────────────────────────┐
   │  Clave MAESTRA (primary key)                                  │
   │    · RSA/ECDSA/EdDSA. Firma. Certifica las subclaves.         │
   │    · Con la que firmás.                                        │
   ├───────────────────────────────────────────────────────────────┤
   │  SUBCLAVE DE CIFRADO                                          │
   │    · RSA o ElGamal (cifrado).                                 │
   │    · Para los que te escriben A VOS.                          │
   ├───────────────────────────────────────────────────────────────┤
   │  SUBCLAVE DE FIRMA                                            │
   │    · DSA/RSA/EdDSA.                                           │
   │    · Para firmar los key ID de las claves de los demás.       │
   └───────────────────────────────────────────────────────────────┘

   ★ La SEPARACIÓN de la clave de firma de la de cifrado es el innovation
     clave: una clave que solo firma NO puede cifrar (y una que solo
     cifra no debería firmar). Es "separación de privilegios".

El proceso de enviar correo con PGP (ocho pasos):

   EMISOR                                RECEPTOR
   ───────                                ───────

   1. Firma:
      H(m) ──► [mi subclave de firma] ──► σ

   2. Cifrado de σ y m:
      [clave pública de Beto (RSA)] ──► (σ ‖ m) cifrado

   3. Agrega metadatos (armored):
      ── BEGIN PGP MESSAGE ──
      m = 65, σ = 2790, kp_emit = 3233
      ── END PGP MESSAGE ──

   4. Envía por SMTP normal. El servidor de correo transporta
      texto ilegible.
                              ◀──── mensaje cifrado ────

   5. Descifra con su clave privada (RSA): recupera (σ ‖ m)

   6. Verifica con la clave pública de Ana (la que trae el
      mensaje, con su key ID): σ^e mod n = H(m)?
      SÍ → "el mensaje es de Ana y está íntegro"
      NO → mensaje alterado o de otro emisor

   7. Extrae la clave pública de Ana del mensaje mismo
      (va firmado con la subclave de firma de Ana).

El problema de la web of trust (gráfico de confianza), que se pregunta:

   Cada usuario tiene un key ID. Los usuarios se FIRMAN entre sí
   (el "key signing party"):

       Ana ──firmada por──▶ Beto ──firmada por──▶ Carla
         ▲                                    ▲
         └────────────────────────────────────┘
              Ana y Carla se confían indirectamente

   ★ Problema: ¿qué pasa si Ana firma la clave de Beto pero
     Beto es un atacante? Y la clave "modelo de confianza" de
     PGP: solo son válidas las firmas de claves que están en un
     keyserver confiable.

   ★ RESPUESTA MODERNA (2019+): el modelo de confianza de Web of Trust
     quedó OBSOLETO. Lo que se usa ahora es:
       · la llave pública se verifica FUERA DE BANDA (imprenta, QR,
         Signal Safety Numbers, servidor de correo conocido);
       · o la FIRMATURE por la cadena de CA (PDF/A-3 signatures,
         firma de código de paquete).

Y ojo con esto en 2026: PGP (OpenPGP) sigue siendo un estándar, pero por problemas históricos de confianza en el modelo de web of trust y por el asunto pgp4u/GnuPG (2023), el mundo de la mensajería pasó a Signal (protocolo Signal, doble ratchet) o a Matrix (MLS). En un examen de 2026, si te preguntan sobre cifrado de mensajería, la respuesta moderna es extremo a extremo con identidad fuera de banda, no "confiá en la firma de la clave".

1.5 IDS, IPS y DPI

Los cuatro componentes

   ┌─────────────────────────────────────────────────────────────┐
   │  (1) FUENTES      tráfico de red, logs, eventos del host    │
   │                   (NetFlow, sFLOW, syslog)                   │
   ├─────────────────────────────────────────────────────────────┤
   │  (2) SENSORES     equipos que analizan (NIDS, HIDS)         │
   │                   patrones, firmas, heurísticas              │
   ├─────────────────────────────────────────────────────────────┤
   │  (3) MOTOR DE     compara contra las reglas;               │
   │      ANÁLISIS     correlaciona eventos;                     │
   │                   puntúa (IDS:Score)                        │
   ├─────────────────────────────────────────────────────────────┤
   │  (4) RESPESTA     el operador (IDS) o el equipo             │
   │                   (IPS: bloquea automáticamente)             │
   └─────────────────────────────────────────────────────────────┘

IDS vs. IPS: la diferencia es una línea

   IDS  (Intrusion DETECTION System)
   ────────────────────────────────
   Está MIRANDO. Detecta y AVISA.
   El tráfico PASA IGUAL.

   ┌────┐  ──trama sospechosa──▶  [IDS]  ──▶ 🚨 ALERTA al operador
   └────┘                                        │
   └────┘  ──sigue igual──────▶  [destino]     el operador decide

   ★ VENTAJAS:  no interrumpe el tráfico bueno; si el IDS falla,
     solo perdés visibilidad.
   ★ DEBILIDAD: el ataque PASA. Si el operador no mira, no pasa nada.

   IPS  (Intrusion PREVENTION System)
   ───────────────────────────────────
   Está EN el camino. Detecta y BLOQUEA.

   ┌────┐  ──trama sospechosa──▶  [IPS]  ──▶ 🛑 DESCARTADA
   └────┘

   ★ VENTAJAS:  frena el ataque en el momento.
   ★ DEBILIDAD: si el IPS se cuelga y se pone en modo "fail-open",
     pasa TODO. Si se pone en "fail-close", corta el servicio legítimo.
     Es un punto único de falla.

El compromiso real: el IPS tiene que estar en línea (inline), y eso significa que es un punto único de falla y un cuello de botella de rendimiento. El IDS, en cambio, se puede poner en un puerto espejo (span port), que no toca el tráfico: ve una copia. La respuesta completa al examen es esa: IDS en puerto espejo (seguro pero no bloquea), IPS en línea (bloquea pero es punto único de falla).

Los dos criterios de decisión

Criterio Question Por qué importa
¿Punto? ¿Dónde está en la red? NIDS (red), HIDS (host), WIDS (inalámbrico)
¿Cuándo? ¿Cómo detecta? por firma (patrón conocido) vs. por anomalía (estadística)

Y el problema central de todo IDS: el falso positivo.

   ¿FALSO POSITIVO?   = alerta de un ataque que NO hay
   ¿FALSO NEGATIVO?   = un ataque que NO se detecta

   El problema clásico: en un centro de cómputos grande hay
   ~10 000 eventos de seguridad POR DÍA. Si el 95 % son falsos
   positivos, el operador deja de mirar en una semana.

   ★ El refinamiento: el "IDS Score" (eNSP) — puntúa cada evento
     por la probabilidad de ataque y lo ordena por prioridad.
     Así el operador mira los 10 más graves, no los 10 000.

Y los dos estilos de respuesta:

   (a) INTERRUPTIVA  (active response)
       el IPS hace ALGO para frenar el ataque:
         · bloqueo del atacante
         · terminate la sesión TCP
       ★ RIESGO: convertir un ataque en un DoS propio.

   (b) PASIVA        (passive response)
       el IPS solo registra y AVISA; que otro sea el que frene.
       ★ más seguro, pero más lento.

DPI: Deep Packet Inspection

   IDS/IPS  compara el PAQUETE contra FIRMAS.
             "¿hay un 'EICAR' en esta conexión?"

   DPI     ABRE el paquete, lo DECODIFICA, y lo interpreta
           como si fuera tráfico de aplicación.

           ┌───────────────────────────────────────────┐
           │  Capa 1-4:  IP  TCP/UDP                   │
           │  ┌─────────────────────────────────────┐  │
           │  │ Capa 7:  HTTP GET /index.html        │  │
           │  │  ... el DPI lee la URL, los          │  │
           │  │  headers, incluso el TLS (con las    │  │
           │  │  claves o en un proxy MITM)          │  │
           │  └─────────────────────────────────────┘  │
           └───────────────────────────────────────────┘

   ★ Lo que permite:
     · policy de Application (permitir Facebook, bloquear
       un juego)
     · detección de malware
     · filtrado de spam
     · INSPECCIÓN DE CONTENIDO cifrado  ← acá está el
       problema gigante (clasificados vs. privacidad)

⚠️ El problema de DPI con cifrado. Hoy todo está cifrado (HTTPS), así que un DPI en el medio no puede leer el contenido. Para hacerlo: 1. Proxy MITM con las claves del servidor (que hoy no se puede con cifrado de extremo a extremo). 2. Instalar la certificación de una CA propia en cada dispositivo (esto es lo que hacen losINAfiltered de empresa y las redes de wireless). 3. Descifrado en el endpoint (instrumentación del navegador).

Es la tensión central de la seguridad de red hoy: confinarse el tráfico a la red ya no es posible sin romper el cifrado de extremo a extremo. Y por eso muchos países (la UE con ePrivacy, el Network neutrality) lo han limitado con leyes.

1.7 IP Móvil

El problema

   El nodo MÓVIL (MN) tiene una DIRECCIÓN PERMANENTE (home address = IP fija),
   que pertenece a su RED LOCAL (home network).

   Cuando se va a otra red (foreign network), cambia de IP.
   PERO sus interlocutores (CN = correspondent node) siguen hablando con la
   HOME ADDRESS.

   El problema: los paquetes para la HOME ADDRESS van a la HOME NETWORK, y no
   llegan al MN. El MN no recibe nada. Se rompe la conexión TCP.

   ★ La identidad del MN es su HOME ADDRESS. Y la identidad viaja con él
     en todos los sistemas. ¿Cómo se hace para que siga funcionando?

Los cuatro componentes (esto es EXACTAMENTE la respuesta al Examen 2008-12 P3)

   ┌──────────────────────────────────────────────────────────────┐
   │                                                              │
   │   MN ──────── Home Network ──────── Home Agent             │
   │  (nodo      (red local del         (el router de la         │
   │   móvil)     nodo móvil)            RED LOCAL, que           │
   │                │                  "actúa como proxy"        │
   │                │                       │                     │
   │                │                   se REGISTRA              │
   │                │                   cuando llega              │
   │                                                              │
   │   MN ──────── Foreign Network ──── Foreign Agent            │
   │                  │                   (el router de la         │
   │                  │                    RED VISITADA)           │
   │                                      │                       │
   │                                      │ recibe el registro     │
   │                                      │ y avisa al HOME AGENT   │
   │                                      ▼                       │
   │                                   COA (Care-Of Address)      │
   │                                   = la IP que tiene el MN   │
   │                                     en la red foránea        │
   │                                                              │
   │   CN ───────── Correspondent Node                            │
   │   (con el que el MN se comunica, p.ej. un servidor web)      │
   │                                                              │
   └──────────────────────────────────────────────────────────────┘

La tabla de roles que hay que saber de memoria:

Componente Qué es Rol
MN (Mobile Node) el host que se mueve tiene dos direcciones: permanente (la de casa) y care-of (la temporal)
HA (Home Agent) el router de la red local hace de proxy del MN: guarda su ubicación y reenvía los paquetes que llegan a la home address
FA (Foreign Agent) el router de la red foránea recibe el registro del MN y le notifica al HA
CN (Correspondent Node) el otro extremo (servidor, peer) habla con la home address del MN

Y las dos direcciones del MN:

   HOME ADDRESS (permanente):  172.16.0.5   ← siempre la misma
                                    ↕
                          SON DISTINTAS
                                    ↕
   CARE-OF ADDRESS (temporal):  172.172.0.17  ← cambia con cada red

Los tres modos de operación

   (1) MODO SIMPLE (sin foreign agent)
   ──────────────────────────────────
   El MNOBTIENE care-of address por DHPCS o SLAAC, y se REGISTRA
   DIRECTAMENTE con el HA.

   El MN ──REGISTRATION──▶ HA      "estoy en 172.172.0.17, TTL = 300 s"

   ┌──────────┐                     ┌──────────┐
   │   MN     │──── registro ──────▶│   HA     │
   │ home:     │                     │          │
   │ 172.16.0.5│                     │ guarda:  │
   │ care-of:  │◀── binding ack ───│ MN@      │
   │ 172.172.  │                     │ COA      │
   │   0.17    │                     └──────────┘

   ★ El MN se mete solo en la foreign network.

   (2) MODO CON FOREIGN AGENT  ← el del Examen 2011-02
   ─────────────────────────────────────────────
   El MN NO puede obtener una dirección: la pide al FA,
   que le ASIGNA la care-of address.

   ┌──────────┐                     ┌──────────┐
   │   MN     │──── registro ──────▶│   FA     │
   │          │◀─ COA = 172.172.0.17│          │
   └────┬─────┘                     └────┬─────┘
        │                                │
        │                                │ "el MN está acá, en 172.172.0.17"
        │                                ▼
        │                           ┌──────────┐
        └──────────────────────────▶│   HA     │
              (el paquete del MN      │          │
               pasa por el FA y        │ crea el │
               llega al HA)           │ TÚNEL   │
                                    └──────────┘

   ★ El MN queda "dentro" del FA: usa la red interna del FA.

   (3) MODO CORRESPONDENT  (CN actualizado)
   ─────────────────────────────────────
   Se le AVISA al CN cuál es la care-of address del MN, para que el
   CN mande directo al MN y no pase por el HA. Se evita el túnel.

   ★ Es la forma más eficiente pero la más compleja de implementar.

Los dos mensajes que hay que saber:

Mensaje Quién → Quién Contenido
Binding Update MN → HA (o MN → FA → HA) "mi care-of address es X, con TTL de 300 s"
Binding Acknowledgement HA → MN "recibí tu registro, vigente hasta las 15:34"

La ruta triangular — el problema conceptual central

Acá está el 90 % de los puntos de los problemas de IP Móvil.

   ESCENARIO: MN está en la foreign network. El CN (servidor)
   está en la INTERNET (ni en la home ni en la foreign).

   ¿Cómo llega un paquete del CN al MN?

   ── RUTA TRIANGULAR (lo que hace IP Móvil) ──

        CN                HA              FA              MN
        │                 │               │               │
        │──paquete────────▶│               │               │
        │  (destino:      │               │               │
        │   HOME ADDRESS  │               │               │
        │   del MN)       │               │               │
        │                 │──TÚNEL────────▶│               │
        │                 │  (destino:     │               │
        │                 │   CARE-OF ADDR)│               │
        │                 │               │──paquete──────▶│
        │                 │               │               │
        │◀────────paquete──────────────────│──paquete──────│
        │                 │               │               │

   ★ Los paquetes HACEN UN TRIÁNGULO: CN → HA → FA → MN, y de vuelta.
     El HA desvía el tráfico al túnel.

   ── ¿POR QUÉ ES NECESARIA? ──
   Porque el CN no sabe la care-of address del MN.
   Los paquetes del CN van a la HOME ADDRESS, y el HA es el
   único que sabe dónde está el MN ahora.

   ── EL PROBLEMA: "routing triangular"  ──
   El tráfico va y vuelve por la red INTERNA del operador.
   Hay trTransit link entre HA y FA. Y el CN está en Internet.

   ★ El problema es que el tráfico de ida y el de vuelta PUEDEN
     tomar caminos DISTINTOS → ASIMETRÍA. Eso rompe algunos
     protocolos y confunde a los middleboxes.

La solución que da el Examen 2011-02 (y es lo que hay que escribir): implementar un túnel entre el HA y el FA, de forma escalable: no modificando los routers intermedios (que sería no escalable) sino encapsulando los paquetes que el HA le manda al FA. O sea, cuando el HA reenvía al COA, en vez de mandar el paquete pelado, le pone un encabezado IP extra con origen IP_HA y destino IP_FA. Así:

  • El paquete del CN al MN viaja: [IP_or:CN, IP_des:HOME_MN] → HA lo envuelve: [IP_or:HA, IP_des:FA][IP_or:CN, IP_des:HOME_MN] → FA lo desenvuelve y lo entrega al MN.
  • El paquete del MN al CN viaja directo: [IP_or:COA_MN, IP_des:CN]. No pasa por el HA.

Escalable porque requiere solo configurar los dos routers extremos (HA y FA), sin tocar los intermedios. Y sin túnel, el paquete del MN al CN haría el mismo camino dos veces, y el TTL lo descartaría.

⚠️ Actualización a 2026 — por qué esto no se desplegó

Esta es una de las piezas de reencuadre más importantes del curso.

   Mobile IPv4  (RFC 5944, 2010) ─┐
   Mobile IPv6  (RFC 6275, 2011) ─┴─→ SIGUEN EN STANDARDS TRACK. NO SON OBSOLETOS.
                                    ╰─→ PERO NO SE DESPLEGARON.

   ¿POR QUÉ NO?
   1. COMPLEJIDAD: requiere modificar el MN, el HA y el CN. Cada operador
      tendría que soporte todo el stack. IPv6 va aún más lejos con la migración.
   2. MIDDLEBOXES: NAT, firewalls y load balancers en el camino rompen el
      túnel porque "no entienden" la hipótesis del túnel.
   3. CGN: en el mundo real hay CGNAT (Carrier-Grade NAT). El HA no puede
      ver al CN porque ambos están detrás de NAT.
   4. ROAMING ENTRE TECNOLOGÍAS: pasar de 4G a 5G a WiFi a 5G rompe la
      dirección. IP Móvil asume una red, no una tecnología.

   ── ¿QUÉ SE USA EN 2026 EN SU LUGAR? ──
   · VPN  (WireGuard, IPsec): simple, funciona, oculta todo.
   · CGN + IPv6: la dirección ya no importa tanto.
   · QUIC connection migration (RFC 9000 §9): la industria resolvió la
     movilidad EN LA CAPA DE TRANSPORTE, no en la capa 3.

   ★ EL CAMBIO DE PARADIGMA: el Connection ID (RFC 9000 §5.1) hace que
     la identidad de la conexión DEJE DE SER LA IP. Eso habilita:
       (a) migración de conexión (cambiás de WiFi a 5G sin cortar)
       (b) NAT rebinding sin romper (el NAT cambia el puerto, QUIC no se rompe)
       (c) balanceo en servidores (varios servidores, un Connection ID)

Para el examen: si te piden IP Móvil, respondé como en 2011 (el modelo con HA, FA, COA, ruta triangular es lo que se evalúa), PERO agregá una línea al final diciendo que en la práctica se reemplazó por VPN + QUIC migration, y por qué. Esa última línea es la que te distingue.

2.1 Ejercicio 1 — El túnel doble del Examen 2008-08

Datos. Una empresa tiene dos sedes: LAN A = 172.16.1.0/24, LAN B = 10.1.1.0/24. Los routers R1 (200.1.1.1) y R2 (200.1.1.2) están unidos por Internet. Un host H_A (172.16.1.5) manda a H_B (10.1.1.3).

Resolución — los dos encabezados, en cada punto del camino:

   ═══ EN LA LAN A ═══
   ┌───────────────────────────────────────────────────────────┐
   │ ENCABEZADO INTERNO (el del paquete original):              │
   │   IP_or  = 172.16.1.5    IP_des = 10.1.1.3              │
   │   MAC_or = MAC(H_A)       MAC_des = MAC(R1)               │
   │   Protocolo = TCP, puerto 80                              │
   └───────────────────────────────────────────────────────────┘

   R1 lo encapsula:
   ┌───────────────────────────────────────────────────────────┐
   │ ENCABEZADO EXTERNO (el del túnel):                        │
   │   IP_or  = 200.1.1.1     IP_des = 200.1.1.2              │
   │   Protocolo = 47 (GRE)                                    │
   ├───────────────────────────────────────────────────────────┤
   │ ENCABEZADO INTERNO (el del paquete original):              │
   │   IP_or  = 172.16.1.5    IP_des = 10.1.1.3              │
   │   MAC_or = MAC(R1)        MAC_des = <next-hop en Internet>│
   └───────────────────────────────────────────────────────────┘

   ═══ EN INTERNET ═══
   Los routers de Internet MIRAN SOLO el encabezado externo:
   200.1.1.1 → 200.1.1.2. No saben ni les importa qué hay adentro.

   ═══ EN LA LAN B ═══
   R2 desenvuelve, quita el externo, y reencola:
   ┌───────────────────────────────────────────────────────────┐
   │ ENCABEZADO INTERNO:                                        │
   │   IP_or  = 172.16.1.5    IP_des = 10.1.1.3              │
   │   MAC_or = MAC(R2)        MAC_des = MAC(H_B)              │
   └───────────────────────────────────────────────────────────┘

Lo que muestra este ejercicio: la dirección MAC cambia en CADA salto (porque es de capa 2), pero la dirección IP origen/destino interna NO cambia nunca durante todo el túnel. El túnel no es NAT: no traduce, solo encapsula.

2.2 Ejercicio 2 — Calcular qué capa corta cada ataque

Enunciado. Una red corporativa tiene: switches gestionables, un router de borde con ACLs, un firewall con IPS, DNS interno, y HTTPS obligatorio por política. ¿Qué ataques quedan contenidos y por qué?

Resolución — la tabla de decisión:

Ataque ¿Lo corta? Por qué
Sniffing ✅ HTTPS obligatorio: todo el tráfico útil va cifrado. El cable es público.
ARP poisoning ✅ port security en los puertos de acceso +DAI: si una MAC aparece en dos puertos, se bloquea el puerto.
Rogue DHCP ✅ DHCP snooping: solo los puertos "confiables" (los de los uplinks) pueden ser servidores DHCP.
IP spoofing ✅ ACL anti-spoof en el borde + uRPF: permit ip 172.16.0.0 0.0.0.255 any en la interfaz interna.
Secuestro BGP ✅ RPKI: se valida el ROA del prefijo antes de aceptarlo.
Secuestro DNS ✅ DNS interno + DNSSEC hacia afuera + validación de SAN en HTTPS: si el DNS devuelve una IP de otro, el certificado no matchea y el navegador aborta.
Rogue CA / MITM TLS ✅ HTTPS obligatorio + no instalar CAs + CT logs. ★ Si el admin de la empresa instala una CA propia, eso es un backdoor.
Ping of Death ✅ el borde filtra paquetes con longitud o flags inválidos.
Denegación de servicio (volumen) ❌ NINGÚN firewall lo detiene. Si alguien te manda 100 Gbps, no hay defensa local. Se necesita upstream (anti-DDoS,anycast).

La fila que hay que subrayar: la última. Un firewall no detiene un ataque de denegación de servicio por volumen, porque para hacerlo tendría que ser más rápido que el atacante. Eso se resuelve aguas arriba, en el proveedor de tránsito, con scrubbing o anycast. Un IDS/IPS es una defensa de escritorio, no una defensa de infraestructura.**

2.3 Ejercicio 3 — Por qué un hash no da confidencialidad (demostración)

Enunciado. Beto tiene un hash de una contraseña. ¿Qué puede hacer un atacante?

Resolución:

   Sistema:   H(password) = SHA-256(password), almacenado.
   ─────────────────────────────────────────────────────────────
   SI el atacante tiene SOLO el hash:
     → PUEDE probar contraseñas contra el hash (ataque de
       diccionario). PEOR que con texto plano, porque
       no puede recuperar la original, pero SÍ puede
       verificar si una candidata es correcta.

   SI el atacante tiene el hash Y la contraseña:
     → el hash NO le dice cuál es la contraseña. Pero puede
       USAR EL HASH como si fuera la contraseña:
         · muchos sistemas comparan el hash del hash
           (el login hash H(password); si H' == H'
           comparando hashes, sirve);
         · sistemas con HASH COMO TOKEn: mandás el hash
           como contraseña y entrás.
       ★ Esto se llama "pass-the-hash".

   SI la contraseña es corta o común:
     → el atacante la saca en segundos (GPU: 10^10/s con SHA-256).

   ── LO QUE LO SOLUCIONA ──
   · SALT (salt): un valor aleatorio por usuario, concatenado
     antes del hash. H(password || salt). Hace que dos
     contraseñas iguales den hashes distintos.
   · KDF LENTO: bcrypt / scrypt / Argon2. 100 000× más lento
     que SHA-256. Una GPU que hace 10^10 SHA-256/s hace
     10^5 bcrypt/s: la diferencia ES la defensa.

Este ejercicio conecta con el WPA2 de la clase 43: WPA2 con PSK suffers justamente del problema del (2): la contraseña se deriva y se puede atacar por diccionario offline. Y WPA3 con SAE resuelve precisamente eso: el protocolo de Dragonfly hace que no se pueda verificar una contraseña candidata offline a partir del handshake capturado. Es el mismo problema, resuelto con un protocolo en lugar de una KDF más lenta.

3.1 ⭐ Examen 2011-02, Problema 2 (30 puntos) — IP Móvil

Fuente: Examen sirc1102, 3 de febrero de 2011. Link: https://www.fing.edu.uy/inco/cursos/redescomp/examenes/sirc1102.pdf

Enunciado (resumen del original)

Se tiene un nodo móvil (MN) que se mueve entre WLAN1+LAN1 y WLAN2+LAN2. El CN está en LAN3. Se pide: (a) los campos MAC/IP de cada segmento cuando el paquete va del MN al CN; (b) lo mismo cuando va del CN al MN, en cada modo de operación; y (c) qué pasa con los campos IP según el modo.

Resolución — parte a) y b) en tabla

Caso A: MN en WLAN1/LAN1, todo en su home network.

   MN ──[WLAN1]── AP ──[LAN1]── R1 ──[LAN3]── CN
   (MN es      (bridging)        (rutea)
    local)
Segmento MAC origen MAC destino IP origen IP destino
WLAN1 MAC1 (MN) MAC4 (AP) 172.172.0.17 203.203.203.3
LAN1 MAC1 (MN) MAC2 (R1) 172.172.0.17 203.203.203.3
LAN3 MAC8 (R1) MAC9 (CN) 172.172.0.17 203.203.203.3

Lo que muestra la tabla: la IP origen/destino no cambia en ningún salto (es un paquete normal, MN y CN están "directamente visibles"). Lo único que cambia es la MAC, en cada router (es de capa 2). En WLAN1 la MAC destino es la del AP (porque la trama es inalámbrica y el primer salto es el AP). En LAN1 es la de R1.

Caso B: MN en WLAN2/LAN2, con foreign agent.

Segmento MAC origen MAC destino IP origen IP destino
WLAN2 MAC1 (MN) MAC7 (FA) 172.172.0.17 203.203.203.3
LAN2 MAC1 (MN) MAC5 (router) 172.172.0.17 203.203.203.3
LAN3 MAC8 (R) MAC9 (CN) 172.172.0.17 203.203.203.3

Ojo con la MAC destino del primer tramo: es la del foreign agent, porque el MN entra a la red foránea a través del FA. Y el CN nunca cambia su IP destino: sigue siendo la home address del MN, porque el MN "se hace pasar" por estar en casa.

Resolución — parte c) y ii) el túnel

El problema (que el enunciado pide resolver): cuando el MN está en la foreign network y el CN quiere mandarle un paquete, lo manda a la home address. Ese paquete viaja por Internet hasta el HA. El HA ve que el MN está registrado con COA = 172.172.0.17, así que debería reenviarlo ahí.

El problema: si el HA lo reenvía sin túnel, el paquete sale por la red pública con destino 172.172.0.17 (una IP privada). Los routers de Internet no pueden rutear una IP privada y descartan el paquete. O peor: el next hop lo devuelve, y el paquete vuelve al HA: un loop, hasta que se descarta por TTL.

La solución: el túnel HA → FA.

   El HA, en vez de mandar el paquete pelado al COA, lo ENCAPSULA:

   ┌──────────────────────────────────────────────────────┐
   │ ENCABEZADO DEL TÚNEL:                               │
   │   IP_or  = 111.1.1.1   (dirección PÚBLICA del HA)  │
   │   IP_des = 222.1.1.1   (dirección PÚBLICA del FA)  │
   ├──────────────────────────────────────────────────────┤
   │ ENCABEZADO INTERIOR (el paquete del CN):             │
   │   IP_or  = 203.203.203.3   (el CN)                  │
   │   IP_des = 172.172.0.17    (home address del MN)    │
   └──────────────────────────────────────────────────────┘

   ★ Ahora los routers de Internet PUEDEN rutear: 111.1.1.1 → 222.1.1.1
     son dos IPs públicas.
   ★ El FA desenvuelve y le entrega al MN (que está en su LAN interna).

Y lo que dice la solución oficial sobre por qué el túnel no es "escalable":

"…y es posible y escalable pues sólo requiere la configuración de dos routers."

El razonamiento completo:

  • Si en vez de túnel se quisiera "arreglar" el problema con rutas estáticas en todos los routers intermedios, haría falta configurar cada router de la red del operador, uno por uno. Eso es NO escalable: con 500 MN hay que mantener 500 rutas en cada router, y cada vez que un MN se mueve hay que actualizar todas.
  • Con el túnel, el problema se resuelve en los dos extremos (HA y FA). Los routers intermedios no necesitan saber NADA: solo reenvían según su tabla, y la tabla dice "de 111.1.1.1 a 222.1.1.1, siguiente salto…". Eso ya existe porque es una conexión común entre dos puntos.

Y los casos de la parte c), en tabla:

   ┌──────────────┬──────────────────────────┬──────────────────────────┐
   │              │ MN → CN                  │ CN → MN                  │
   ├──────────────┼──────────────────────────┼──────────────────────────┤
   │ Caso A       │ IP_or = 172.172.0.17     │ IP_or = 203.203.203.3   │
   │ (en home)    │ IP_des = 203.203.203.3  │ IP_des = 172.172.0.17    │
   │              │ (normal, sin túnel)      │ (normal, sin túnel)      │
   ├──────────────┼──────────────────────────┼──────────────────────────┤
   │ Caso B       │ IP_or = 172.172.0.17     │ 1er tramo:               │
   │ (en foreign, │ IP_des = 203.203.203.3  │   IP_or = 203.203.203.3  │
   │  route       │ (sale directo a         │   IP_des = 172.172.0.17  │
   │  triangular)│  Internet, NO pasa por HA)│   (va al HA)             │
   │              │                          │ 2do tramo (túnel):       │
   │              │                          │   IP_or = 111.1.1.1 (HA) │
   │              │                          │   IP_des = 222.1.1.1 (FA)│
   │              │                          │   encapsula: CN → MN     │
   └──────────────┴──────────────────────────┴──────────────────────────┘

El detalle conceptual que hay que decir explícitamente: el paquete MN → CN en el caso B no pasa por el HA. Sale directo del MN a Internet con destino el CN. Esto se llama ruta triangular: CN → HA → FA → MN (ida) y MN → CN directo (vuelta). La asimetría es el problema: el mismo paquete de ida y vuelta puede tomar caminos distintos, lo cual rompe la idea de "extremo a extremo". Por eso existe el modo "correspondent": notificarle al CN la COA para que los dos caminos sean directos.

  2. El binding tiene un TTL (típicamente 300 s). El MN lo renueva periódicamente. Si no renueva, el HA deja de desviar y el MN tiene que re-registrarse. Es lo mismo que el lease de DHCP, aplicado a la mobilidade.

3.3 Examen 2007-07, Pregunta 5 (5 puntos) — funcionamiento de IP Móvil

Resolución. Es la versión corta de §3.2, en cinco puntos:

  1. El MN sale de su red local con su home address y no se registra con nadie todavía: simplemente se mueve.
  2. Cuando llega a una red foránea, obtiene una care-of address (por DHCP, por SLAAC en IPv6, o del foreign agent si lo hay).
  3. El MN manda un Binding Update al HA: "mi care-of address es X, con TTL de 300 s". Si hay un FA en el medio, el Update pasa por él.
  4. El HA recibe, registra y acusa (Binding Acknowledgement). Desde este momento, el HA sabe dónde está el MN.
  5. Cuando llega un paquete del CN con destino = home address del MN, el HA lo intercepta (está en su red local), lo encapsula en un túnel hacia el FA (con destino = COA), y el FA lo entrega al MN.

Tope para 5 puntos: los 5 pasos, con los nombres de los mensajes (Binding Update, Binding Ack, COA, home address) y quién se registra con quién.

📌 Resumen del Bloque F y del curso entero en 10 líneas

  1. TLS = cifrado + integridad + autenticación + forward secrecy, con handshake de 1 RTT en TLS 1.3. 443/TCP. Cifra con clave de sesión (EC)DH, autentica con el certificado.
  2. SSH = el mismo esquema con PFS por claves efímeras, Ed25519 por defecto, y canal de control multiplexado.
  3. PGP = cifrado extremo a extremo con clave maestra separada de la de cifrado; clave pública verificada fuera de banda.
  4. Túnel = encapsular con dos IP, así el paquete cruza una red que no lo entiende. Enrutado (routers de Internet miran solo la IP externa) vs. conmutado (el switch mira MACs).
  5. IDS avisa (en puerto espejo, no interrumpe); IPS bloquea (en línea, es punto único de falla). DPI abre y decodifica, y con cifrado requiere MITM o CA instalada.
  6. Ningún mecanismo de capa 2/3 es frontera de seguridad — la única defensa real contra MITM es la criptografía de la capa 7.
  7. IP Móvil: MN, HA, FA, CN; home address + care-of address; el HA hace de proxy y desvía por un tunnel hacia el FA; ruta triangular es el problema central y el túnel lo resuelve sin tocar los routers intermedios.
  8. En 2026, IP Móvil no se desplegó: lo reemplazaron VPN + QUIC migration + el Connection ID, que saca la identidad de la IP.
  9. Punto de corte por capa: capa 2 → port security/DAI/DHCP snooping; capa 3 → ACL/uRPF/RPKI; capa 7 → TLS (la única real).
  10. La idea que cierra el curso: cada capa resuelve un problema y crea otro; la seguridad de una red es la suma de las defensas, y la única que no se puede rodear es la que no depende de la red: la criptografía de extremo a extremo.

                deliver_data(pkt.datos)

                udt_send_broadcast(construir(esperado, 0, ACK))

            else

                // pido que me reenvíen desde `esperado`

                // NO lo entrego todavía: para mantener el orden
            }
        }

**Lo que hay que justificar (esto es lo que da los 30 puntos):** - **El `ack` es CUMULATIVO** (no individual): si recibo `ack(m)`, recibo **todo hasta `m`**. Así se evita un ACK por cada paquete, y es exactamente lo que hace TCP. - **El emisor guarda `pending`** (los enviados sin confirmar) para poder **retransmitir** los que se perdieron. - **El receptor usa `esperado`** para **entregar en orden**: si recibe `seq > esperado`, **no lo entrega** (entregaría fuera de orden) y manda un **NAK** pidiendo el que falta. **(c) Los tres casos:** **Caso 1 — Se pierde un ACK.** El emisor **no lo sabe** (no hay confirmación de llegada del ACK). Después del **timeout**, retransmite el paquete. La **eliminación de duplicados** la da el número de secuencia (`esperado`): todo lo que tenga `seq < esperado` ya salió. **Caso 3 — Se pierde el propio paquete de datos.** El receptor ve que falta un número (si recibe el `n+1` antes que el `n`, detecta el hueco) → manda un **NAK por `esperado`**, y el emisor (que tiene `esperado` en `pending`) lo retransmite. Si el emisor ya no tiene nada en `pending` (porque el ACK anterior cubrió ese paquete), espera el **timeout** y reenvía. **Y si no hay NAK, el próximo paquete que llegue con hueco también dispara un NAK.** > **Tope para 30:** (a) el encabezado con 5 campos justificados, (b) los dos > procedimientos en pseudocódigo con el `ack` cumulativo y `pending`, (c) los 3 > casos con qué pasa en emisor y receptor. 1. ¿Qué clave cifra los datos en TLS 1.3? ¿Y para qué sirve la clave que va en el certificado?

Respuesta **La clave de sesión simétrica**, acordada por **(EC)DHE** (X25519 en la práctica) derivada con HKDF, es la que cifra los datos de aplicación. **Nunca se transmite**: los dos la calculan a partir del secreto compartido. **La clave pública del certificado no cifra los datos**: se usa para **autenticar al servidor**. El servidor firma con su privada, el cliente verifica con la pública del certificado, y eso descarta el *man-in-the-middle*. En TLS 1.2 la clave del certificado tenía **dos** usos: autenticar **y** cifrar el *pre-master secret*. En **TLS 1.3 el transporte de clave con RSA fue eliminado** (`RFC 8446`): todo el secreto se negocia con (EC)DHE.

2. ¿Por qué un IDS y un IPS son decisiones distintas y no se pueden sustituir?

Respuesta Porque **están en puntos distintos de la red y resuelven problemas distintos**. El **IDS** va en un **puerto espejo** (*span port*): ve una **copia** del tráfico, no lo toca. **No puede bloquear nada**, pero **tampoco puede romper nada**: si el IDS falla o se cuelga, lo único que se pierde es visibilidad. Su salida es una **alerta** a un operador. El **IPS** va **en línea** (*inline*): es parte del camino. **Puede bloquear**, y por eso es mucho más eficaz contra un ataque en curso. Pero es un **punto único de fallo**: si se cuelga, o el tráfico pasa (*fail-open*, menos seguro) o se corta todo (*fail-close*, se cae el servicio legítimo). Y es un **cuello de botella de rendimiento**, porque tiene que analizar **todo** el tráfico. La respuesta completa: **se usan los dos, en paralelo** — IDS para visibilidad y para el análisis forense posterior, IPS para la defensa en tiempo real.

3. ¿Por qué el túnel de IP Móvil es escalable y las rutas estáticas en los routers intermedios no?

Respuesta Porque **el túnel se resuelve en los dos extremos**. El problema: el HA tiene que hacer llegar un paquete al MN, cuya **care-of address** (`172.172.0.17`) es una **IP privada**. Los routers de Internet **no rutean IPs privadas**: la descartan o la devuelven al remitente, generando un **loop** hasta que el TTL lo mate. **Rutas estáticas**: para arreglarlo habría que **programar cada router de la red del operador** para que sepa que "de la red del MN a la IP privada hay que seguir por esta interfaz". Con 500 MNs, son 500 rutas **por router**, y cada vez que un MN se mueve hay que **actualizar todos los routers**. Eso es **inmantenible**. **Túnel**: el HA le pone **un encabezado IP extra** al paquete, con origen = la IP **pública** del HA y destino = la IP **pública** del FA. Ahora los routers de Internet rutean normal: solo ven "de 111.1.1.1 a 222.1.1.1", que ya es una ruta que existe. El FA quita el encabezado externo y entrega el original al MN. Se configura **una vez** en el HA y **una vez** en el FA. Los routers intermedios **no se tocan**. Eso es escalable.

4. ¿Qué es el forward secrecy y por qué en TLS se logra con (EC)DHE y no con RSA?

Respuesta **Forward secrecy** significa que **el secreto de la sesión no se puede recuperar después**, aunque alguien se quede con el material del servidor **hoy**. **Cómo se logra en TLS 1.3:** las claves de sesión se derivan de un **intercambio (EC)DHE efímero**. Cada sesión usa claves públicas **nuevas**, que se descartan al terminar. El servidor **nunca guarda** el secreto compartido. Por eso, si te entregan el disco forense del servidor **ahora**, **no podés descifrar** lo que se habló **ayer**: las claves privadas nunca existieron juntas dos veces. **Por qué no con RSA:** en el TLS antiguo, el *pre-master secret* venía cifrado con la clave pública del servidor y **quedaba guardada en el servidor** para poder descifrar las sesiones. Si te AGREDA el servidor, tenías las claves y podías descifrar **todo el histórico**. RSA **no da forward secrecy** por sí solo. La misma regla aplica a Diffie-Hellman: **estático no da FS** (ataque Logjam), **efímero sí**.

5. ¿Qué diferencia hay entre sniffing y ARP poisoning en términos de capa y de defensa?

Respuesta **Sniffing** es un ataque **pasivo**: te ponés a escuchar. No modifica nada, no genera tráfico, y es **indetectable** para la víctima. Vive en **capa 2/3** (el medio compartido) o **capa 7** (el protocolo). La única defensa real es el **cifrado de la capa de aplicación (TLS)**: si todo está cifrado, el sniffing ve bytes incomprensibles. **ARP poisoning** es un ataque **activo de capa 2**: el atacante manda tramas ARP falsas para **modificar la tabla ARP** de la víctima y así lograr que envíe el tráfico a él en lugar de al gateway real. Se resuelve con **port security** (limitar cuántas MACs por puerto), **DAI** (validar las tablas ARP), y **segmentación en VLANs**. **La diferencia clave:** el sniffing se rompe **con cifrado** (capa 7); el ARP poisoning se rompe **con control de acceso a la capa 2**. **Son defensas completamente distintas**, y esa es la respuesta que hay que dar.

6. ¿Por qué la IP Móvil (MIPv4/MIPv6) no se desplegó, si sigue en Standards Track?

Respuesta Porque **técnicamente funciona pero operacionalmente es inviable**. Las cuatro razones: 1. **Complejidad**: requiere que **el MN, el HA y el CN** soporten todo el stack de movilidad. 7. ¿Qué es DPI y por qué tiene un problema estructural hoy?

Respuesta **DPI** (*Deep Packet Inspection*) es un mecanismo que **abre el paquete, decodifica sus capas y lo interpreta como si fuera tráfico de aplicación**: lee la URL de un HTTP, los headers, o incluso descifra el TLS. Sirve para aplicar **política por aplicación** (permitir el trabajo, bloquear un juego), detectar malware y filtrar spam. **El problema estructural:** hoy **prácticamente todo** el tráfico está cifrado (HTTPS). Un DPI en el medio **no puede leer el contenido** — es criptográficamente imposible sin la clave. Para hacerlo tiene solo tres caminos: 1. **Proxy MITM** con las claves del servidor: **imposible** con cifrado de extremo a extremo. 2. **Instalar una CA corporativa** en cada dispositivo: **técnicamente funciona**, pero es **instalar una puerta trasera** en cada máquina, y viola la privacidad. 3. **Descifrar en el endpoint** (instrumentación del navegador o del SO): solo funciona si controlás el equipo. Y hay una tercera capa: si la **app** usa cifrado de extremo a extremo (Signal, WhatsApp), el cifrado ocurre **dentro** de la app y **nadie en la red** — ni el administrador, ni el gobierno — puede leerlo. **Por eso hay leyes** (la *ePrivacy* de la UE) que **limitan** el uso del DPI para inspección de contenido.

8. Un switch tiene port security y una MAC puede aprenderse solo una vez. ¿Qué pasa si un atacante hace flooding de MACs?

Respuesta Se llama **MAC flooding** (o **CAM table overflow**), y el ataque tiene dos fases: 1. **Llenar la tabla.** La tabla CAM del switch tiene un **tamaño finito** (por ejemplo, 8 000 entradas). El atacante manda tramas con **MACs de origen aleatorias** hasta llenarla. 2. **Forzar al switch a actuar como un hub.** Cuando la tabla está llena, el switch **no puede aprender** la MAC destino, y por eso **reenvía la trama por TODOS los puertos** (como un hub). A partir de ahí, el atacante **ve todo el tráfico** de la VLAN. **Las defensas:** - **Port security** con límite de MACs por puerto: al superar el límite, el puerto entra en `shutdown` o `restrict` y **se genera un aviso**. - **Dynamic ARP Inspection (DAI)**: valida los paquetes ARP contra el **DHCP snooping binding database**, y descarta los ARP con IP-MAC inconsistentes. - **DHCP snooping**: solo los puertos "confiables" (los uplinks) pueden actuar como servidores DHCP; así se corta el *rogue DHCP*. - **VLAN**: separar los puertos de usuarios de los de gestión y de los de servidores. **Y el detalle importante:** el ataque **sí** es posible porque el switch no tiene "puertos seguros" **por defecto**. Por eso el 802.1X + port security + DHCP snooping + DAI se ven **siempre juntos** en cualquier red empresarial bien armada.
