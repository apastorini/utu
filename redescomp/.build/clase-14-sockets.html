PARTE 1 — TEORÍA

1.1 Qué es una API, y por qué la capa 4 se programa así

La capa de transporte es la primera en que el sistema operativo implementa servicios para los procesos. Antes (física, enlace, red) los datos viajan sin que ningún proceso los pida: un paquete de red es un paquete, va a donde diga la cabecera IP y a nadie le importa quién lo pidió.

A partir de TCP/UDP aparecen las questions: "¿este datagrama es para el navegador o para el correo?". Como la CPU tiene un solo programa ejecutándose a la vez, el SO necesita un mecanismo para:

  • que un proceso reserve un puerto y así pedirle al mundo "lo que llegue por este número es mío";
  • entregar cada segmento que llega al proceso correcto;
  • permitir que un proceso espere o intente enviar sin bloquear la CPU entera.

Ese mecanismo se llama socket. Y el conjunto de llamadas que el SO expone para usarlo se llama la API de sockets, que en Unix viene de Berkeley (BSD) y es el mismo en Linux, macOS y Windows (con diferencias de nombres).

Dato clave para el examen: la API de sockets nunca fue parte del protocolo TCP/IP. Es una interfaz del sistema operativo. Por eso el mismo puede hablar TCP o UDP según qué creaste: el protocolo lo decide el y el /, no el código de aplicación.

Qué es un socket, en una frase

Un socket es un par de descriptores de archivo más un estado: el SO mantiene por cada socket las direcciones involucradas, el buffer de envío, el de recepción y la tabla de rutas interna (para TCP, el estado de la conexión completa).

En Unix, un socket es un número entero (el file descriptor), y por eso funciona con read(), write() y close() como cualquier archivo. Eso no es un detalle: es la razón de que la API sea tan simple.

1.3 y el orden de bytes

La estructura

c struct sockaddr_in { sa_family_t sin_family; // AF_INET para IPv4 in_port_t sin_port; // puerto, EN ORDEN DE RED struct in_addr sin_addr; // IP, EN ORDEN DE RED // ... y un padding para que sea del tamaño de sockaddr };

El problema que resuelve

Las redes y las máquinas usan ordenes de bytes distintos:

  • big-endian (network byte order): el byte más significativo primero. Es el estándar de todas las redes.
  • little-endian (host byte order): el byte menos significativo primero. Es lo que usan x86, ARM en su modo normal, y prácticamente toda computadora de escritorio.

Si guardás el puerto 80 como número y lo mandás sin convertir:

` Puerto 80 en decimal = 0x0050

En little-endian en memoria: [ 50 ] [ 00 ] ← se manda primero el 0x50 Lo que recibe la red: 0x5000 = 20480 ← ¡puerto equivocado! En big-endian en memoria: [ 00 ] [ 50 ] ← correcto `

Por eso existen las conversoras:

Función Qué hace
host → network, short (16 bits, puertos)
network → host, short
host → network, long (32 bits, direcciones IP)
network → host, long

Se usan igual en cliente y servidor. No es "el servidor convierte y el cliente no". Los dos lados convierten, porque los dos escriben en un formato de red. Esto es una pregunta de examen clásica y casi todos la contestan mal.

1.4 Multiplexación y demultiplexación: el papel de

Aunque la teoría profunda está en la Clase 16, el punto de conexión con esta clase es uno solo y es el que más se pregunta:

` El SO mantiene una TABLA que asocia:

(protocolo, IP local, puerto local) → file descriptor

Cuando llega un datagrama UDP de la red: 1. el SO lee el puerto destino de la cabecera UDP 2. busca en la tabla (IP, puerto) 3. si está, ENTREGA los bytes al proceso dueño de ese fd 4. si no está, lo DESCARTA y a veces manda ICMP port unreachable `

es lo que inscribe una fila en esa tabla. Sin del lado servidor, no hay fila, y todo lo que llega se descarta.

El caso de TCP es un refinamiento: la tabla tiene — la 4-tupla — porque dos clientes distintos pueden estar conectados al mismo puerto 80.

`c int main(void) { int fd, fd_cli; struct sockaddr_in dir; char buf[100];

fd = socket(AF_INET, SOCK_STREAM, 0);

memset(&dir, 0, sizeof dir); dir.sin_family = AF_INET; dir.sin_port = 80; / <-- falta htons /

Resolución — los 3 errores:

  1. ** dir.sin_port = 80; sin htons. En little-endian, 80 = 0x0050 se escribe en memoria, y al enviarlo al cable el otro extremo lee 0x5000 = 20480. El servidor queda escuchando en el puerto 20480. El error clásico.**
  2. ** y sobre el fd del listening socket.** Hay que usar fd_cli, el descriptor que devolvió accept. Con fd el comportamiento no es lo que uno espera, y lo que corresponde al socket pasivo no es el eco.
  3. ** con en la dirección** — eso está permitido, pero si después querés responder por no vas a saber a quién. Con TCP usás sobre la conexión, así que es aceptable; no es error, es una decisión.

2.5 Ejercicio 2 — ¿Por qué el del servidor es obligatorio?

Pregunta: el servidor UDP de arriba hizo al puerto 5000. ¿Qué pasaría si lo sacáramos?

Resolución. Sin bind(), el SO le asigna un puerto efímero (típicamente entre 32768 y 60999 en Linux). El cliente no tiene forma de saber cuál es, porque:

  • no está en ningún protocolo de descubrimiento;
  • el cliente UDP no recibe nada hasta que envía primero;
  • y no hay ningún mensaje de error que le diga "el servidor está en el puerto X".

O sea: el servidor quedaría escuchando en un puerto que nadie conoce, y el servicio sería inaccesible. En TCP esto se(compensa parcialmente) porque el cliente conoce el puerto 80 por convención; en UDP no hay puerto conocido por convención.

Por eso es obligatorio en el servidor y opcional en el cliente.

2.6 Ejercicio 3 — Dos procesos en el mismo puerto

Pregunta: ¿qué pasa si dos procesos hacen al mismo puerto TCP?

Resolución. Sin SO_REUSEADDR, el segundo bind() falla con ("address already in use"). Eso es lo correcto: dos procesos no pueden atender el mismo puerto, porque las conexiones llegarían a cualquiera de los dos al azar.

Con (en Linux también ), ambos pueden hacer bind y el SO reparte las conexiones entrantes entre ellos según el hash de la 4-tupla. Es lo que usan los servidores nginx para tener N workers. Ojo: en TCP no permite que dos sockets escuchen al mismo tiempo y roben traffic de forma insegura; en UDP sí es peligroso, porque cada datagrama se lo lleva un proceso cualquiera.

📌 Resumen

  1. Un socket es un par de descriptores de archivo más un estado que el SO mantiene: direcciones, buffers y (en TCP) la tabla de la conexión.
  2. La API de sockets no es parte de TCP/IP: es del sistema operativo.
  3. Servidor TCP: → → → → → /. ** devuelve un fd NUEVO.**
  4. Cliente TCP: → → /. Sin ni .
  5. UDP: , /, no hay ni , y es lo que te dice quién te mandó el datagrama.
  6. / en los dos lados: la red es big-endian y el host little-endian. Sin la conversión, el puerto 80 llega como 20480.
  7. es obligatorio en el servidor (si no, queda en un puerto efímero que nadie conoce) y opcional en el cliente.
  8. Sin , un segundo al mismo puerto falla con .
  9. La clave real de demux del kernel es la 5-tupla; la "2-tupla de UDP" es la simplificación clásica. QUIC la reemplaza por el Connection ID.

✅ Autoevaluación

1. ¿Por qué el servidor TCP hace pero el cliente no?

Respuesta Porque **fija la dirección local**. El servidor necesita un puerto **conocido por todos** (el 80 por convención), o nadie podría conectarse. El cliente no: él **conoce** el puerto del servidor, y su propio puerto es irrelevante para el servidor, así que lo deja que el SO le asigne como **efímero**. En UDP la distinción es más tajante: sin del lado servidor **nadie sabría a qué puerto enviar**, porque en UDP el cliente no tiene a quién "preguntar".

2. Si escribís dir.sin_port = 80; sin htons, ¿qué puerto queda escuchando el servidor? ¿Y si la máquina fuera big-endian?

Respuesta En little-endian (x86, ARM en modo normal): el puerto queda en **20480**, porque se escribe al revés y al enviarlo se lee `0x5000 = 20480`. En una máquina big-endian **no pasa nada**: el orden ya coincide, y por eso el bug aparece en algunas máquinas y en otras no — que es la peor forma de bug. La solución correcta es **siempre** usar `htons()`, sin importar la arquitectura.

3. ¿Qué devuelve y por qué el descriptor que devuelve no es el mismo que se le pasó?

Respuesta Devuelve **un file descriptor nuevo**, dedicado a **esa** conexión concreta, y además llena la dirección del cliente que se le pasó por puntero. El descriptor original sigue siendo el "socket de escucha" y se usa **únicamente** para el próximo `accept()`. La razón es que un proceso puede tener **muchas** conexiones simultáneas: cada una necesita su propio descriptor para poder atenderla por separado.

4. ¿Qué dos funciones de la API no existen para UDP, y por qué?

Respuesta y `accept()`. Las dos existen para **administrar la cola de conexiones pendientes** de un servicio con conexión. En UDP **no hay conexión**: no hay handshake que completar, no hay estado que establecer y no hay "pendiente de aceptar". Cada datagrama es independiente y se entrega si el socket está ahí. A cambio, UDP tiene /, que son a la vez "enviar" y "a quién", porque sin conexión el destino hay que indicar en **cada** llamada.

5. ¿Por qué la solución oficial de usa para comparar con "COMMIT", y qué hay que usar?

Respuesta Porque el autorapid733 trata como si comparara **contenido** de cadenas, y lo que compara en C son **direcciones de memoria**: dos literales idénticos pueden estar en direcciones distintas, así que el resultado es **indefinido** y casi siempre falso. Además el literal va sin comillas, así que ni siquiera compila. Lo correcto es ****.

6. En el problema de connectCheaper(), ¿qué problema tiene el hecho de que los lleguen al puerto 12345 pero las respuestas (/) no regresen allí?

Respuesta El socket del usuario está **eado al puerto 12345**. Cuando manda el al AP, el AP le responde **al puerto efímero** del socket (el que el SO le asignó) y **no** al 12345. La solución oficial no resuelve ese desajuste: si el escucha en 12345, se va a quedar esperando respuestas que nunca llegan ahí. Hay dos soluciones correctas: hacer un ** a otro puerto efímero** para la fase de conexión, o usar **** sobre el socket UDP (que existe y hace que las respuestas del mismo destino lleguen por ese socket).
